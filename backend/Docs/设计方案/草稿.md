### 一、 第一性原理：我们到底要“蒸馏”什么？

这是最核心的一点，千万不能搞错：
我们之前测试已经证明了，小模型是个“记不住百科全书的差生”。
所以，**我们微调的目的，绝对不是把《我的世界合成表》重新硬塞进它的脑子里！** （因为参数量小，塞进去它还是会记混、会幻觉）。

**我们要蒸馏（教给它）的，是“工作流（Workflow）”和“逻辑格式（Format）”。**

**打个比方：老师傅带徒弟**
*   **错误微调：** 让徒弟（小模型）把《汽车维修手册》（MC合成表）死记硬背下来。徒弟脑容量小，背着背着就背串了，把修轮胎的方法用在了修发动机上。
*   **正确微调：** 给徒弟发一本《汽车维修手册》（这就是我们刚决定的 **Python 工具层+JSON字典**）。老师傅（Gemini大模型）示范给徒弟看：“遇到客人说车坏了，你**第一步**先翻开手册第10页查故障码，**第二步**照着手册的步骤去拿扳手，**第三步**输出标准的维修报告单。”

**你真正要收集的数据对是这样的：**
*   **输入 (Input)：** 玩家说“做把木镐” + Python工具返回 `{"木镐": "3木板+2木棍", "背包": "空"}`
*   **输出 (Output) (来自Gemini的完美回答)：** `[Thought: 玩家要木镐，查阅数据发现需要木板和木棍，背包为空。Plan: 1. 寻找树木 2. 挖掘原木 3. 合成木板...]`

你是在教小模型**“如何阅读工具返回的数据，并按标准格式下达指令”**，而不是教它游戏本身的常识。只要格式和逻辑对了，由于数据是外挂工具给的，它就**永远不会产生幻觉**！

### 二、 需要无数个小模型吗？还是一个就行？

你问到了 Agent 架构的痛点：“每个负责不同的 agent，是不是要加载好几个模型？我的显存/内存吃得消吗？”

**答案是：只需要 1 个基础小模型（Base Model），配合“多顶帽子（LoRA）”。**

这里要引入一个微调界的神级技术，叫做 **LoRA (Low-Rank Adaptation)**。

用通俗的话解释：
假设你电脑里跑着一个 8B 的本地 Llama 模型，这就是一个“通用打工人”。
你不需要为了 Router（路由）、Planner（规划）、Executor（执行）去训练三个完全独立的大模型（那样太占内存了）。
你只需要提炼出三个 **LoRA 权重文件**（你可以把它们理解为三个**极小的“职业面具”或“外挂芯片”**，每个可能只有几十 MB）。

*   **工作流程：**
    1. 玩家说话了。系统给 Llama 戴上 **“Router 面具 (LoRA 1)”**，Llama 瞬间变成无情的分类机器，输出 JSON 意图。
    2. 意图传给 Python 工具层，查好字典。
    3. 系统把 Llama 的面具摘下来，换上 **“Planner 面具 (LoRA 2)”**，Llama 看了看字典数据，瞬间变成车间主任，输出分步计划。

这样，你在显存里**始终只运行着一个基础大模型**，只是在不同的代码节点，瞬间切换它头上的“面具”。这种方法不仅极其节省资源，而且每个 Agent 的专业能力都极强（因为专职专训）。

  1. _do_collect_block("crafting_table")

  在 bot 周围 32 格内，扫描已加载世界，找最近一个 block id 等于 crafting_table 的方块。

  - name
  - position.x
  - position.y
  - position.z

  - minecraft-data 提供“工作台的标准方块 ID”

  - 找到后得到它的真实坐标
  - 然后 collectBlock.collect(block) 负责走过去、挖掉、拾取
