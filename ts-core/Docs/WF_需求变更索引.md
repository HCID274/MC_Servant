## 2026-04-24 — Triage（分诊） 架构演进备案：状态注入 + Composite Output（复合输出）

- 来源：用户针对"当前 triage（分诊） 把 chat（闲聊） / task（任务） / cancel（取消） 分开是否会锁死未来"的追问，需要明确当前最小实现的演进路径，避免后续再次讨论同一问题。
- 核心判断（写这条的前置）：
  - 当前 triage（分诊） 的"单 intent（意图） 分叉"不是架构内在约束，只是 T-023（任务二十三） / T-024（任务二十四） 阶段的最小实现选择。
  - 用户提出的两类担心在架构层面已有解法，只是未在当前任务白名单内落地。
  - "一句话带回复+动作"（如 "过来这里喵~"）在当前已通过 plan（规划） 产出 `reply`（回复） + `skill_call`（技能调用） 实现，**不是缺口**。
  - "Bot（机器人） 主动边做边说"属于 BotActor（机器人执行代理） 事件广播路径，和 triage（分诊） 无关，**不在本条覆盖范围**。
- 演进阶段一：**chat_reply（闲聊回复） 注入 actor（执行代理） 状态快照**（解决"工作时被闲聊，回复却不知道自己在干嘛"）
  - 问题现状：当前 `chat_reply`（闲聊回复） 路径是无状态 LLM（大语言模型） 调用，用户问"你在干嘛"时，bot（机器人） 会回"我在和你聊天喵~"而不是"我正在挖矿喵，已经挖到 3 个钻石了~"。
  - 做法：
    - BotActor（机器人执行代理） 提供一个 ~50~100 token（文本配额） 的当前状态快照接口（例如"当前正在执行: 挖矿 (已进行 2 分钟, 已获得 3 个钻石)"）。
    - 在构造 `chat_reply`（闲聊回复） 的 system prompt（系统提示词） 时注入该快照。
    - 快照仅用于回复生成，不进入 triage（分诊） 决策，避免与意图分类耦合。
  - 工程点：
    - 快照采集不应阻塞主写者路径，建议用单写者出口广播出来的最新事件做一层只读投影（projection），chat_reply（闲聊回复） 读投影。
    - 快照失效/为空时的降级：无状态闲聊，不强制要求快照存在。
  - 建议落点：**挂在 T-025（任务二十五） 扩技能任务的后期**，或开一个 T-025.5（任务二十五点五）。理由：多技能上线后，"用户问进度"的场景会立即出现；没有状态注入会造成用户困惑。
  - 复杂度评估：低。不涉及协议变更，不涉及新 worker（工作线程），只加一个只读投影 + prompt（提示词） 注入。
- 演进阶段二：**triage（分诊） 输出从单 intent（单意图） 升级为 composite（复合）**（解决复合意图消息语义丢失）
  - 问题现状：当前 triage（分诊） 输出 `{intent: "chat" | "task" | "cancel"}` 是互斥单选。对于"别走那边，危险，回来"这类**同时包含取消 + 回复 + 新任务**的消息，当前会被迫二选一，语义必丢。
  - 做法：
    - triage（分诊） 输出升级为可组合结构：
      ```
      {
        cancel?: { reason: string, priority: "interrupt" | "queued" },
        reply?: string,
        action?: { skill: string, params: {...} } | { sandbox_code: string }
      }
      ```
    - 字段独立，任意组合。
    - route（路由） 层按字段存在与否依次派发：先 cancel（取消） 中断，再 reply（回复） 出站，再 action（动作） 入队。
  - 工程点：
    - route（路由） 派发需要严格定义顺序（建议：cancel → reply → action），避免"先动作后取消"这类自相矛盾的执行。
    - worker（工作线程） 层**不用改**，因为 worker 本来就按不同队列处理；只是入口派发变聪明。
    - triage（分诊） 提示词要升级，但仍然是单次 LLM（大语言模型） 调用，成本增量可控。
    - 向后兼容：旧的 `{intent}`（单意图） 输出可被自动转换成 composite（复合） 结构，灰度期两套共存。
  - 建议落点：**T-026（任务二十六） 观测/回放之后的独立任务，或与 T-027（任务二十七） 沙箱重启合并**。理由：composite（复合） 输出让 sandbox_code（沙箱代码） 可以和 reply（回复） / cancel（取消） 共存，是 T-027（任务二十七） 的自然前置。
  - 复杂度评估：中。涉及契约变更（`contracts.ts`（契约定义））、路由层变更、triage（分诊） prompt（提示词） 变更、测试重写。但所有变更都集中在 conversation（对话） 层内部，不扩散到 runtime（运行时） / workers（工作线程） / BotActor（机器人执行代理）。
- 影响评估：
  - 当前 T-024（任务二十四） / T-025（任务二十五） / T-026（任务二十六） **不受影响**，继续按现队列推进。
  - 阶段一落地后，"工作时被闲聊" 缺口即闭合；阶段二落地后，"复合意图消息" 缺口即闭合。
  - 两阶段均**不推翻** 当前 triage（分诊） → route（路由） → worker（工作线程） 的分层结构，只在 triage（分诊） 输出形态和 chat_reply（闲聊回复） 输入形态上做增量升级。
  - 原队列里 `ConversationRouteDecision`（对话路由决策） 的现有契约在阶段二会扩字段，但原有 `chat` / `task` / `cancel` 分支的行为保持向后兼容。
- 待后续确认：
  - 阶段一的 BotActor（机器人执行代理） 状态快照接口是放在 `runtime/bot-actor-projection.ts`（只读投影） 还是直接挂在 BotActor（机器人执行代理） 本体上（建议前者，避免污染单写者路径）。
  - 阶段二的 composite（复合） 派发顺序一旦定稳，是否需要补一条"三者同时存在时的语义规范"文档（例如 cancel（取消） 后 reply（回复） 是否仍要发出）；倾向于"cancel（取消） 发模板回执时 reply（回复） 字段被 LLM（大语言模型） 写入则覆盖模板"。
  - 是否需要把阶段一和阶段二合并成一份 `12_对话架构演进设计.md`（对话架构演进设计） 专门文档，避免后续索引膨胀。

## 2026-04-24 — Sandbox（沙箱） 上下文成本治理：渐进披露 + LRU 热队列 + 经验蒸馏（长线备案）

- 来源：用户针对"JSON（结构化文本） skill_call（技能调用） 比 sandbox_code（沙箱代码） 便宜"这一结论的深入追问，提出了更本质的上下文管理思路。
- 归因修正（写这条的前置）：
  - 之前解释中使用的"手册 vs 菜单"比喻有偏差。函数签名与 JSON（结构化文本） schema（结构约束） 在 token（文本配额） 密度上基本等价，单个 API（接口） 的描述成本差异不大。
  - sandbox_code（沙箱代码） 的真实成本来源是两项，不是一项：
    1. **一次性预加载的 API（接口） 广度**（Facade API（门面接口） 全量签名 + 使用示例 + 安全约束）——此项可被渐进披露治理。
    2. **控制流语法本身的上下文成本**（async（异步）/await（等待）/try/catch（异常捕获）/错误汇报模式等）——即使做了渐进披露，这部分仍难以完全省掉。
  - 因此 T-024（任务二十四） 选 JSON（结构化文本） 路径仍然正确（单动作场景不需要控制流），但后续 T-027（任务二十七） 沙箱重启时，不应无脑沿用"全量 Facade（门面接口） 手册一次性塞入提示词"的旧思路。
- 长线方案一：**LRU（最近最少使用） 热队列 + 渐进披露**（T-027 启动时优先评估）
  - 做法：
    - 启动时只喂最小索引（API（接口） 命名空间列表 + 基础示范 + `describe(namespace)`（按命名空间展开） 调用方式），总预算 200~300 token。
    - 模型按需调用 `describe()` 拉取具体 API（接口） 签名；拉取过的签名进入一条有界 LRU（最近最少使用） 队列，新调用入队，满队踢出最旧项。
    - 队列上限建议按 **token（文本配额） 预算**而非条数（例如 1500 token），因为不同命名空间展开后大小差异大。
  - 需处理的工程点：
    - 冷启动：首次调用的 API（接口） 不在队列时必须触发 `describe()` 拉取，而不是让模型凭猜测写。
    - 跨会话：建议按 `botId`（机器人标识） 持久化热队列，因为同一女仆任务分布连续。
    - 失败保护：`describe()` 拉取失败时的降级路径（回退到全量手册？拒绝执行？）需要明确。
  - 价值判断：能把中等复杂度 sandbox_code（沙箱代码） 请求的输入成本从 ~3000 token 降到 ~800 token 量级，接近 skill_call（技能调用） 成本。
- 长线方案二：**经验蒸馏（"炼丹"）机制**（T-027 之后的增强，不是 T-027 本体）
  - 做法：
    - 每次 sandbox_code（沙箱代码） 任务完整执行后，汇总调用轨迹（任务描述 → 成功代码 / 失败代码 + 失败原因）落库。
    - 使用任务描述的 embedding（向量嵌入） 作为检索键，建立 **skill library（技能库）**。
    - 后续同类任务进来时先检索技能库，命中则跳过试错阶段直接复用或让 LLM（大语言模型） 在已有经验基础上微调，再跑。
  - 先例：NVIDIA（英伟达） Voyager（航海家） 论文（2023）在 Minecraft（我的世界） LLM（大语言模型） agent（智能体） 上实现过完全相同的机制，可直接参考其失败轨迹存储、经验老化、经验验证的设计。
  - 预期收益：女仆任务分布高度重复（挖矿/跟随/回家/打招呼等），检索命中率应很高；命中后复杂任务成本从"每次 3000+ token 试错"降到"200 token 检索 + 直接执行"。
  - 需处理的工程点：
    - 失败经验也要存，避免模型反复犯相同错误。
    - 老化机制：世界版本/地形变化会让老经验失效，需要 TTL（生存时间） 或验证回溯。
    - 检索粒度权衡：存整段代码（好用但泛化差） vs 存"招式骨架"（泛化强但需二次改写）。
    - 复用前的快速自检，防止坏经验污染后续任务。
  - 复杂度评估：比方案一高一个数量级，涉及向量检索基础设施 / 经验存储 schema（结构约束） / 老化策略 / 自检执行器，不适合与 T-027（任务二十七） 一起做。
- 影响评估：
  - 当前 T-024（任务二十四） / T-025（任务二十五） / T-026（任务二十六） 不受影响，继续按现队列推进。
  - T-027（任务二十七） 一旦重启，**必须先评估方案一**，再决定是否沿用原 03_SANDBOX_SPEC.md（沙箱规格） 的"一次性全量 Facade（门面接口） 手册"模式；若采用方案一，需要在 T-027（任务二十七） 拆出 `describe()` 工具与 LRU（最近最少使用） 热队列基础设施。
  - 方案二作为"T-027 之后"的长线增强登记在此，不分配任务号；触发时机：真实运行数据显示 sandbox_code（沙箱代码） 重复率超过某阈值（例如相同任务描述重复 ≥3 次）。
- 待后续确认：
  - 方案一是否作为 T-027（任务二十七） 的硬性前置（"沙箱重启必须带渐进披露"），还是 T-027（任务二十七） 的可选增强（"先按老模式打通，再考虑换成渐进披露"）。
  - 方案二是否需要在更早阶段就预留数据采集钩子（例如从 T-024（任务二十四） 开始就把每次 LLM（大语言模型） 调用的 prompt（提示词） / completion（补全） / 结果 落库），以便将来训练技能库时有数据可用。
  - 是否需要单独开一份 `11_上下文治理设计备忘.md`（上下文治理设计备忘） 承载这两个方案的详细设计，避免后续索引条目继续膨胀。
