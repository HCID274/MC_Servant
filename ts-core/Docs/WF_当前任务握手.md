**为什么必须确认**:
JAR（自定义服务端插件） 桥接会直接影响目录结构、通信协议、消息格式、测试方式和真实 I/O（输入输出） 边界。若 JAR（自定义服务端插件） 端尚未具备发包能力，直接派发真实 WebSocket（全双工通信协议） / TCP（传输控制协议） 对接会迫使 Coder（编码代理） 自行假设协议，风险过高。

**候选方案**:

1. **方案 A：JAR（自定义服务端插件）端尚未具备发包能力**
   - 核心做法：T-039（任务三十九） 只做 TS Core（TypeScript 单核心） 端 `server-bridge`（服务端桥接） 通信骨架、协议契约、mock（模拟）JAR（自定义服务端插件） 端测试与可替换 transport（传输层） 端口。
   - 核心优点：不阻塞 TS Core（TypeScript 单核心） 主干，可先稳定协议边界与测试夹具。
   - 核心缺点：不能证明真实 Paper（服务端） 插件到 TS Core（TypeScript 单核心） 的端到端链路。
   - 适用前提：plugin（插件） 端暂时没有网络发包实现，或尚不能稳定发出握手 / 心跳 / observation patch（观测补丁）。

2. **方案 B：JAR（自定义服务端插件）端已经具备发包能力**
   - 核心做法：T-039（任务三十九） 直接实现 TS Core（TypeScript 单核心） 端最小真实通信接入，包含握手、心跳、基础消息解析、连接生命周期与真实本地联调脚本。
   - 核心优点：最快闭合 Paper（服务端） + plugin（插件） + TS Core（TypeScript 单核心） 的真实 I/O（输入输出） 通路。
   - 核心缺点：需要明确现有 JAR（自定义服务端插件） 端协议形态；若协议仍不稳定，会造成返工。
   - 适用前提：plugin（插件） 端已经能向本机 TS Core（TypeScript 单核心） 发包，并且至少能发送握手 / 心跳 / 最小观测消息之一。
