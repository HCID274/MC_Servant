# 工程规范

> Coder B 自检 + Reviewer C 审查共同遵循的单一规范源。
> 代码必须遵守。如有不可避免的违反,理由必须写在 B 的 500 字交互记录里,由 C 评估是否成立。

---

## 1. 高内聚 (High Cohesion)

- 一个模块 / 文件 / 函数只做一件事
- 模块内部的依赖应比模块之间的依赖紧密得多
- 反例:`utils.ts` 堆了 20 个互不相关的函数

## 2. 低耦合 (Low Coupling)

- 模块间通过明确的契约 (interface / 类型) 交互,不直接读取彼此内部状态
- 不要让 A 知道 B 的实现细节,只让 A 知道 B 的对外签名
- 反例:跨模块直接 import 私有 helper

## 3. DRY (Don't Repeat Yourself)

- 同一逻辑在两处出现 → 提取到共享位置
- 但不要为了 DRY 而 DRY:相似不等于重复,过早抽象会反向增加耦合
- 判断标准:这两处代码的**变更原因**是否一致?一致才是真重复

## 4. SOLID

- **S** 单一职责: 类 / 函数只有一个变化原因
- **O** 开闭原则: 对扩展开放,对修改关闭(新需求加新代码,不改旧代码)
- **L** 里氏替换: 子类型替换父类型不破坏语义
- **I** 接口隔离: 多个小接口胜过一个大接口
- **D** 依赖倒置: 依赖抽象,不依赖具体实现

## 反模式速查

| 反模式 | 解药 |
|---|---|
| god file (上帝文件,500+ 行做多件不相关的事) | 拆分 |
| 隐性耦合 (模块 A 假设模块 B 的内部状态) | 改成显式接口 |
| 过早抽象 (为"未来可能的需求"加抽象层) | 删掉,等真有需求再加 |
| 防御式编程 (在内部代码里检查框架已保证的不变量) | 删 |
| 注释解释 WHAT 而不是 WHY | 删 |
| 类型 `any` | 90% 是偷懒,10% 是真不可避免 |
| 顺手重构 (修 bug 时连带改无关代码) | 一次改一件事 |
| 留 `// TODO` 不写期限 | 要么现在做,要么删 |

## B 自检清单 (强约束)

提交前必查:

1. 改动是否破坏了现有模块的内聚性?(把不属于这里的逻辑塞进来了吗?)
2. 改动是否新增了不必要的跨模块依赖?
3. 改动是否在多处复制了同样的逻辑?
4. 改动是否给 god file 又加了几行?
5. 改动里有没有"防御未来不存在的需求"的代码?
6. 注释里有没有解释 WHAT 而不是 WHY?
7. 有没有 `any` 是真不可避免的?
8. 触碰 Mineflayer（Minecraft 客户端库） API（应用程序接口） 时,是否传入库要求的真实对象类型?例如 `lookAt`（看向目标） 必须用 `Vec3`（三维向量） 实例,不能用普通 `{x,y,z}` 对象冒充。
9. 触碰世界定位 / 多世界缓存时,是否只通过既有 `currentWorld`（当前世界）、`ResourceService`（资源服务） 或 `runtime/transport`（运行时传输层） 接口读取 `world_key`（世界键）?不得自行拼接世界名或猜测维度。
10. `bash scripts/pre_review.sh` 全绿了吗?

---

## C 审查清单 (强约束)

按这个顺序看:

1. **架构层**: 改动有没有违反 `01_ARCHITECTURE.md` 的不可破坏约束?
2. **模块边界**: 改动有没有越界(碰了 A 给的范围之外的模块)?越界是否在 B 的 500 字记录里有合理解释?
3. **工程规范**: 上面 4 条原则,逐条检查
4. **运行时真实对象与世界键**: Mineflayer（Minecraft 客户端库） 调用是否使用真实 `Vec3`（三维向量）/`Block`（方块对象）/`Item`（物品对象）/`Entity`（实体对象） 等库对象?多世界定位是否只走既有世界键接口?
5. **架构 vs 现状冲突**: 看到代码和架构文档矛盾时,**不直接打回**,在反馈里标 ⚠️ 询问用户:是代码偏了,还是架构需要更新?

打回分两类:
- **实现层打回**(代码乱 / 重复 / 耦合) → 退给 B 改
- **方案层打回**(实现违反架构约束) → 退给 A 重拆
