# ENGINEERING_QUALITY_DEBT.md — 工程质量债两批处理备忘

> v0.1 | 2026-05 | 记录当前已识别的工程质量收敛事项；不替代架构文档、任务派发或 `PROGRESS.md`。

## 0. 目的

这份文档只做备忘：把当前已经确认需要处理的工程质量问题按两批保存下来，后续派发任务时以这里为准，避免遗漏或把问题拆碎。

这不是功能排期，也不是要求一次性大重构。每一批真正开工前，仍需要按当前架构文档、代码现状和用户最新目标拆成可执行任务。如果发现架构文档与代码实现冲突，不由执行者自行决定，应回到 Planner A 给出两条路线让用户选择。

## 1. 第一批：执行语义与运行时边界先收敛

第一批优先处理“任务到底如何被 LLM 生成、如何进入沙盒、如何判定完成、如何向用户汇报”的主链路。原因是后续所有 skill、挖掘、合成、脱困和经验沉淀都依赖这条链路。如果这里继续保留旧入口、重复判断和分散语义，后面越做越容易左右脑互搏。

### 1.1 拆分沙盒执行模块

当前问题：沙盒执行模块承担了过多职责，既像代码加载器，又像能力注入器，还混入任务结果读取、完成判断、汇报生成、兼容旧接口等逻辑。这个形态违反高内聚低耦合，也让后续修改 `ensure`、`until`、`report`、动作摘要时很难判断影响范围。

收敛方向：把沙盒执行链路拆成更清晰的职责层，例如执行器、API 注入层、目标条件检查层、动作结果规范化层、用户汇报输入层。每层只做一类事，并通过明确类型传递数据。

验收重点：拆分后在线行为不能退化；沙盒 TS 仍是唯一规划输出形态；错误信息、动作结果、最终汇报仍能被上层拿到；不得重新引入旧的自然语言规划输出或旧式 skill call 输出。

### 1.2 清理旧 `api.bot` / `api.chat` 执行面

当前问题：规划提示词和解析器已经要求输出纯 TS 代码，但沙盒运行时仍可能保留旧的 `api.bot`、`api.chat` 风格能力面。这会让代码层和提示词层互相矛盾：Prompt 要求新范式，运行时却还暴露旧范式，测试也容易继续锁住旧接口。

收敛方向：默认按“纯代码型沙盒执行面”收敛。旧接口如果确实还需要留给历史回放或兼容测试，必须被明确隔离为 legacy/replay-only，不得出现在在线规划可用 API 中。

验收重点：Plan 输出只能是代码；在线执行路径不能鼓励或支持旧式 skill call；测试不再把旧执行面当作主路径行为。

### 1.3 拆分运行时传输层中心化逻辑

当前问题：运行时传输层聚合了过多状态读取、动作转发、世界定位、事件转换和兼容逻辑。它一旦变成中心化大模块，skill、sandbox、conversation 都会绕着它隐式耦合，后续排查 `world_key`、维度、动作卡顿和任务状态时成本很高。

收敛方向：把传输层拆成清晰边界：世界状态读取走既有世界标签接口；动作执行走运行时动作端口；事件和诊断各自有明确出口；业务层不得自行拼接世界名或猜测维度。

验收重点：所有 `world_key`、维度、世界定位仍只通过既有接口获取；不能把世界判断散落到 skill、sandbox 或 prompt；动作执行和状态读取的调用方向要清楚。

### 1.4 收窄 Plan Prompt 中的业务规则堆积

当前问题：Plan Prompt 里承担了太多业务细节，容易把 Minecraft 事实、动作约束、回复风格、异常恢复、上下文使用规则全部塞进同一个提示词。Prompt 越大，越难验证，也越容易出现模型误读，例如把命令解释成自然语言、或错误使用搜索、或忘记最终汇报。

收敛方向：Prompt 只保留硬约束、输出格式、少量正例和必要的行为原则。Minecraft 事实必须来自 `mineflayer`、`minecraft-data` 和实时快照；动作能力由 TS API 表达；复杂完成判断由 `ensure` / `until` 等代码语义承载。

验收重点：Prompt 中不写死配方、掉落、工具等级等 MC 事实；必须重复强调“只输出 TS 代码”这类硬约束；示例应展示正确代码结构，而不是自然语言解释或旧 JSON skill call。

### 1.5 统一动作完成语义、库存增量和汇报输入

当前问题：`mine`、`cutTree`、`ensure`、沙盒完成判断、任务总结都可能各自读取动作返回值、推断收集数量、生成库存变化。这会导致同一个动作在不同层含义不同：有的层认为“动作没报错”就是成功，有的层要求“实际获得数量满足目标”才算成功。

收敛方向：建立统一的动作结果规范化与条件检查机制。单动作如 `mine("stone", 5)` 应表达强语义：没有实际获得足够目标掉落就失败。复杂目标用 `ensure(action, until.xxx(...))` 表达最终验收：执行前记录 baseline，执行后读取真实状态，检查条件，不满足再恢复，仍不满足就结构化失败。

验收重点：`until.gained(...)` 基于执行前后的背包差量；`until.has(...)` 基于当前总量；`until.gainedDropOf(...)` 由运行时事实解析掉落关系，不能让 LLM 背 MC 掉落知识；最终汇报生成应消费统一摘要，而不是每个 skill 自己拼一句机械文本。

## 2. 第二批：公共契约、抽象层与测试兼容面收敛

第二批处理第一批主链路之外的结构性债务。它们不一定立刻阻塞最小闭环，但会影响后续扩展、测试稳定性和审查通过率。第一批没有收敛前，不建议先动第二批的大范围拆分，否则容易在旧执行语义上继续堆抽象。

### 2.1 拆分过胖的 skill 公共端口

当前问题：skill 公共端口承担了过多技能能力、执行结果、上下文对象和跨模块类型。它越胖，新增 skill 越容易直接依赖不该依赖的字段，导致模块边界变模糊。

收敛方向：按能力维度拆分端口，例如动作执行、资源查询、物品与背包、世界状态、用户汇报、诊断记录等。skill 只依赖自己需要的最小接口，而不是拿到一个全能上下文。

验收重点：新增或修改 skill 时不需要引入大而全依赖；公共类型不承载业务捷径；跨层调用方向符合架构文档。

### 2.2 收敛 Craft / Placement 抽象与重复白名单

当前问题：合成和放置已经出现抽象层，但如果真实能力还没有接上，或者白名单散落在多个模块，就会形成“看起来有服务，实际仍靠各处硬编码”的半成品结构。

收敛方向：Craft 负责配方查询、材料检查、调用 mineflayer 合成；Placement 负责寻找可放置位置、执行放置和缓存工作台位置。白名单只限制 Phase 1 允许的目标范围，不承载配方事实。

验收重点：配方事实来自 `minecraft-data` / mineflayer；工作台放置不写进高阶流程里；白名单集中配置，不在 prompt、skill、runtime 多处重复。

### 2.3 拆分 Conversation 规划执行处理器

当前问题：规划执行处理器如果同时负责输入解析、上下文拼接、LLM 调用、Plan 解析、ExecJob 构造、执行启动、事件记录和错误降级，就会变成新的中心化入口。出问题时很难判断是分诊、提示词、解析器、执行器还是日志的问题。

收敛方向：把对话入口拆成可测试的小段：输入归一化、上下文装载、LLM 调用、代码解析、执行任务构造、执行结果处理、用户可读汇报。每段保留必要诊断日志，线上路径保持异步，避免游戏动作线程被 LLM 延迟卡住。

验收重点：每次 LLM 调用记录总延迟、首字延迟、模型、输入摘要和输出摘要；简单动作也走统一 TS 代码执行路径；任务完成后必须有用户可读汇报。

### 2.4 收敛跨层兼容入口

当前问题：为了迁移方便，部分数据层、运行时层、领域层可能保留兼容入口。如果这些入口继续被新代码直接调用，就会让边界失效，形成“表面有端口，实际到处穿透”的结构。

收敛方向：兼容入口只能服务历史迁移、旧数据读取或测试适配。新业务代码应通过 core ports、runtime ports、ResourceService、world-model 等架构认可的接口访问能力。

验收重点：新实现不直接依赖迁移兼容对象；兼容层命名和注释明确；如果必须越界调用，需要记录原因并在审查中评估是否接受。

### 2.5 迁移保留旧行为的测试

当前问题：测试可能仍然以旧 `api.bot`、旧 skill call、旧 JSON 任务形态作为正确行为。这会导致代码即使按新架构收敛，也被旧测试拉回去。

收敛方向：把测试分成主路径测试和 legacy 兼容测试。主路径测试应验证纯 TS 代码输出、沙盒执行、结构化失败、真实完成判断、最终汇报；legacy 测试如果保留，必须明确说明只覆盖历史兼容，不代表推荐接口。

验收重点：测试不再鼓励旧 API；新增测试围绕新执行语义；涉及 LLM、Prompt、对话路由或在线入口的改动，必须按仓库规则做真实 OpenAI 兼容 API 验收或记录不可达时的人工手测步骤。
