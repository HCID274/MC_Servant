## 0. 这份文档怎么看

这份文档把项目按“竖状树”展开。每一行后面的 `←` 表示这个目录或文件在当前系统里的职责。

阅读顺序建议：

1. 先看第 1 节的总树，建立整体地图。
2. 再看第 2 节的 `src`（源码）树，这是当前主线代码的核心。
3. 最后看第 3-6 节的运行链路树，理解信息怎么从入口流到机器人动作。

```text
├── .dockerignore                    ← 容器构建忽略规则

├── .env.example                     ← 环境变量样例
├── scripts/

```

### 1.1 顶层文件职责

| 文件 | 作用 |
|---|---|
| `agent.md` | 所有 Agent（智能体）进入仓库后的索引入口，说明项目定位、Phase 1（第一阶段）边界和文档导航。 |
| `README.md` | 给人类和运行环境看的使用说明，覆盖 `pnpm dev`（开发运行）、`pnpm build`（构建）、`pnpm start`（运行构建产物）、`pnpm db:migrate`（数据库迁移）。 |
| `package.json` | 当前工程的命令中心和依赖清单；真实可执行入口是 `src/main.ts`（进程入口），库导出入口是 `src/index.ts`（库入口）。 |
| `drizzle.config.ts` | `Drizzle Kit`（数据库迁移工具）读取的迁移配置，复用数据层配置约定。 |
| `Dockerfile` | 只打包 `ts-core`（TypeScript（类型脚本）核心工程）自身，不打包 `Redis`（缓存）、`PostgreSQL`（关系型数据库）或 `Minecraft`（我的世界）服务端。 |

### 3.2 关闭链路

```text
SIGINT/SIGTERM（进程关闭信号）
└── runtime.close（在线运行时关闭）
    ├── ConversationWorker.close（关闭对话工作线程）
    ├── BotWorker.close（关闭机器人工作线程）
    ├── AppRuntimeCoreResources.close（关闭运行时核心）
    │   ├── BotActor.shutdown（切换机器人执行代理到关闭状态）

    ├── AppRuntimeServices.close（关闭服务层）
    │   ├── Fastify.close（关闭接口网关）
    │   └── WorkerBullmqRuntime.close（关闭三条任务队列）
    └── AppRuntimeResources.close（关闭基础设施）
        ├── Redis.close（关闭缓存客户端）
        └── Postgres.close（关闭关系型数据库连接池）
```

## 4. 消息信息流树

### 4.1 HTTP（超文本传输协议）消息入口

```text
外部请求 POST /api/message（消息提交接口）
└── interfaces/server.ts（接口服务器）
    ├── 校验 bot_id/message_id/content（机器人标识/消息标识/内容）为非空字符串
    ├── 校验请求 bot_id（机器人标识）必须等于当前运行时 bot_id（机器人标识）
    └── app/bootstrap.ts 中注入的 message handler（消息处理器）
        ├── createConversationWorkerTask（创建对话工作线程任务）
        ├── workers.conversation.queue.add（写入 msg:{botId}（消息队列））
        └── createMessageAcceptedResponse（返回 202（已接受）响应）
```

### 4.2 ConversationWorker（对话工作线程）处理

```text
msg:{botId}（消息队列）
└── workers/conversation-worker.ts
    ├── cloneWorkerTask（克隆并校验任务载荷）
    ├── parseDeterministicGoToCommand（解析“去 x y z”确定性命令）
    ├── triage（分诊）
    │   ├── 命中“去 x y z” → task/normal（任务/普通）
    │   └── 未命中 → 默认 chat/normal（闲聊/普通）或使用注入分诊器
    ├── createConversationRouteDecision（创建对话路由）
    │   ├── chat_reply（闲聊回复）
    │   ├── cancel_interrupt（取消中断）
    │   ├── plan_exec（规划执行）
    │   └── modify_interrupt_then_plan（修改后中断再规划）
    └── 根据路由执行动作
        ├── chat_reply（闲聊回复）
        │   ├── createConversationReply（创建模板回复）
        │   └── broadcastReplySink → BotActor.broadcastReply（机器人执行代理广播聊天）
        ├── plan_exec + goTo（规划执行 + 前往坐标）
        │   ├── createSkillCallJob（创建技能调用任务）
        │   ├── createBotWorkerTask（创建机器人工作线程任务）
        │   └── enqueueExecTaskSink → bot:{botId}:exec（执行队列）
        └── 其他规划路径
            └── planner_unavailable（规划器不可用）记录为丢弃事件
```

### 4.3 BotWorker（机器人工作线程）执行

```text
bot:{botId}:exec（执行队列）
└── workers/bot-worker.ts
    ├── cloneBotWorkerTask（克隆并校验机器人任务）
    ├── cloneExecJob（克隆执行任务）
    │   ├── skill_call（技能调用）→ 校验技能名和参数
    │   └── sandbox_code（沙箱代码）→ 校验代码字段，但当前不执行
    ├── intent_epoch（意图纪元）新鲜度检查
    │   ├── 过期 → createBotWorkerActions(discarded)（生成已丢弃动作）
    │   └── 新鲜 → createBotWorkerActions(started)（生成已开始动作）
    ├── actor.executeSkill（机器人执行代理执行技能）
    │   ├── 成功 → completed（已完成） + enqueue_brain（入摘要队列）
    │   └── 失败 → failed（已失败） + 抛错给 BullMQ（任务队列）
    └── actionSink（动作汇点）

```

## 9. 从全局理解这个项目的最短路径

如果只读源码，建议按下面顺序：

```text
1. src/main.ts
   └── 先看进程怎么启动

2. src/app/entrypoint.ts + src/app/bootstrap.ts
   └── 再看所有模块如何被装配成一个在线运行时

3. src/interfaces/server.ts
   └── 看 HTTP（超文本传输协议）消息如何进入系统

4. src/workers/conversation-worker.ts
   └── 看消息如何被分诊成闲聊回复或 goTo（前往坐标）任务

5. src/workers/bot-worker.ts
   └── 看执行队列如何串行调用 BotActor（机器人执行代理）

6. src/runtime/actor.ts + src/runtime/transport.ts
   └── 看唯一写 Minecraft（我的世界）的边界在哪里

7. src/data/schema.ts + src/db/connection.ts
   └── 看持久化和基础设施如何定义
```

一句话总结：当前代码已经把“消息入口、队列削峰、对话工作线程、机器人工作线程、BotActor（机器人执行代理）、Mineflayer（Minecraft 协议客户端）”这条最小链路搭起来了；很多更复杂的能力已经有清晰契约，但还没有接入真实执行。
