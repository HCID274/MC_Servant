# Runtime Control Architecture

> **⚠️ 本文档已被 `ts-core/Docs/01_ARCHITECTURE.md`（第 4 节三层响应模型）和 `ts-core/Docs/02_RUNTIME_SPEC.md`（BotActor 状态机 + 中断协议 + 反射系统）取代。** 本文档中的"混合控制内核"概念已被吸收为 01 的"脊髓→丘脑→皮层"三层模型。本文档仅作早期讨论记录保留。

## 已确认原则

- 运行时采用三层控制模型：
  - 反射层：高频扫描危险与硬约束，必要时直接打断当前执行。
  - 执行层：负责原子动作、过程写入、结果校验与中断收尾。
  - 规划层：基于最新上下文生成受限计划，并在需要时重规划。
- 控制内核采用“混合控制内核”，而不是全局单一有限状态机。
- 反射层不能依赖 `LLM` 才做出第一反应；命中高优先级风险时必须本地立即介入。
- 规划层的主流程固定为 `Plan-Execute-Review`。
- 重规划节奏当前固定为纯事件触发式，而不是周期性唤醒。

## 当前决定

- 被打断后，在新的 `LLM` 决策到达前，允许根据打断原因执行本地应急策略。
- 当前全局组织形式固定为：
  - 反射层规则表：负责硬中断、危险识别与应急策略选择。
  - 计划会话：负责承载一次 `Plan-Execute-Review` 的计划上下文。
  - 步骤执行器：负责执行步骤列表中的原子动作、局部分支与结果校验。
  - 局部状态机：仅允许在少数动作内部使用，不作为全局控制主模型。
- 当前已确认的应急方向：
  - 威胁接近时，优先远离逃跑。
  - 主人主动打断时，先经过小型语义识别，再区分软打断与硬打断。
  - 落入高危环境时，先执行脱险动作；若已具备对应资源，可触发预置自救动作。
- “低威胁先说话，高威胁先保命”是当前运行时优先级原则。
- 面对爆发性威胁时，需要补齐一组本地底层能力：
  - 给定目标怪物名称，查找最近的对应实体。
  - 对目标实体执行距离保持、拉扯与脱离。
  - 对非特殊高危目标，优先复用 `mineflayer` 现成战斗能力。
  - 对特殊高危目标，例如高爆目标，优先保持距离与规避，不默认近战。
- 主人输入进入打断流前，需要先经过一个小型语义识别器：
  - 若识别为软打断：当前动作不立刻停止，只把该表达转述给后续规划层处理。
  - 若识别为硬打断：当前动作立即停止，先执行本地互动表现，再等待新的硬打断规划结果。
- 主人硬打断后的本地互动表现，当前确定为：
  - 立即播放一条预先缓存的卖萌语录。
  - 播放后不恢复旧计划，等待新的规划结果接管。
- 硬打断语录生成时，不注入记忆上下文；该类台词只服务于“已立即停手并准备按刚收到的新指令执行”的瞬时表达。
- 硬打断语录不得重复追问主人下一步，因为硬打断输入本身已经携带新的明确意图。
- 软打断回复不走生成链路，当前固定写死为：`好的，我先记下，让我想想喵~`

## 当前优先级

- 第一优先级：路径失效。
- 第二优先级：目标失效。
- 第三优先级：执行前提失效。
- 第四优先级：系统级异常。
- 上述四类需要先做成可运行的打断、记录与复盘闭环。
- 其他风险与威胁类型本阶段不能删除，必须保留占位与 `TODO`，但实现可后置。

## 互动语录缓冲

- 需要维护一个专门的卖萌语录缓冲队列，用于硬打断与空闲时互动。
- 语录生成应结合记忆上下文完成，不使用固定死板模板作为唯一来源。
- 每次预生成 10 条候选语录，进入专门的数据结构缓存。
- 每条语录都需要带使用标记；一旦被消费，就标记为 `used`，后续不能重复使用。
- 当可用语录数量小于等于 1 条时，应在空闲窗口触发下一轮语录补货。
- 新一轮语录补货时，需要参考：
  - 上一轮已生成的 10 条语录。
  - 避免与已使用或刚生成的内容高度重复。
- 对于硬打断专用语录，补货时不注入记忆上下文，重点只放在语气风格、停手确认与执行承接。
- 语录补货属于后台低优先级任务，只能在不影响主执行与高优先级反射控制时运行。
- 后台补货与类似低优先级生成任务，当前统一采用 `async task` 形式，不引入 `worker thread`。

## 硬打断语录生成规则

- 硬打断语录只服务于“已立即停手并准备按刚收到的新指令执行”的瞬时表达。
- 该类语录不注入记忆上下文，不依赖过去对话细节。
- 该类语录必须表达两件事：
  - 当前动作已经立刻停下。
  - 接下来会按主人刚才的新吩咐执行。
- 该类语录不得重复追问主人下一步，因为硬打断输入本身已经携带新的明确意图。
- 语气固定为轻萌型：有女仆感，但不能夸张、低俗或过于喧闹。
- 长度控制为一句中等长度的话，不要太短，也不要拖成长句解释。

### 硬打断语录生成提示词

```text

1. 只生成一句话，长度中等，不要太短，也不要过长。
2. 语气偏轻萌型，要有女仆感，但不能夸张、不能低俗、不能太闹。
3. 这句话必须表达：
   - 我已经立刻停下来了
   - 我会按主人刚才的新吩咐来
```

### 软打断固定回复

- 当前固定文案：`好的，我先记下，让我想想喵~`

## 威胁与异常分层

- 危险类：优先由反射层本地处理第一反应，再决定是否进入复盘。
- 非危险阻塞类：优先记录异常并触发复盘，不直接套用逃跑策略。
- 当前优先落地的非危险阻塞类：
  - 路径失效：路径规划失败、长时间无进展、被地形卡住。
  - 目标失效：目标实体、方块、容器或交互对象不再有效。
  - 执行前提失效：缺工具、背包满、关键资源不足、当前条件不满足。
  - 系统级异常：断连、插件异常、关键接口失效、运行时错误。
- 当前保留占位但后置实现的危险类与环境类：
  - `TODO`：持续伤害、火焰、中毒、窒息、跌落边缘等环境风险。
  - `TODO`：低血量、低饥饿、护甲不足等生存状态风险。
  - `TODO`：更细粒度的敌对实体分类与针对性战斗策略。

## 四类异常的统一模型

- `path_invalid`、`target_invalid`、`precondition_invalid`、`system_exception` 不再被视为四套分散报错，而是统一收敛为同一个 `ReviewTrigger` 框架下的四种原因。
- 统一闭环固定为：
  - 检测器发现异常。
  - 立即停止当前受影响步骤或运行时会话。
  - 将异常写入增量事实与派生状态。
  - 生成面向复盘层的 `ReviewTrigger`。
  - 由 `Plan-Execute-Review` 中的 `Review` 阶段决定是否重试、换目标、补前提、重连或彻底放弃旧计划。
- 四类异常按照破坏范围分为三层：
  - 步骤级可恢复：`path_invalid`
  - 计划级失效：`target_invalid`、`precondition_invalid`
  - 运行时级失效：`system_exception`
- 只有真正影响计划推进的异常才能升级为 `ReviewTrigger`；普通诊断日志与轻微抖动不能污染复盘流。

## ReviewTrigger 标准结构

- 每个 `ReviewTrigger` 必须至少包含以下字段：
  - `triggerId`：本次复盘触发唯一标识。
  - `reasonCode`：异常原因代码，只允许使用统一枚举。
  - `severity`：严重级别，决定是否允许等待、重试或必须立即停机。
  - `detectedAt`：触发时间。
  - `detectedBy`：检测来源，例如步骤前校验器、路径看门狗、目标验证器、系统健康监视器。
  - `planId`：所属计划会话标识。
  - `stepId`：所属步骤标识；若是运行时级异常可为空。
  - `commandId`：最上层主人命令标识。
  - `activeSkill`：触发时的技能或执行单元名称。
  - `evidence`：最小证据集合，不允许只写一句自由文本。
  - `localRecoveryAction`：复盘前已执行的本地止损动作。
  - `resumePolicy`：旧计划是否允许恢复，以及恢复的前提。
  - `reviewRoute`：进入哪一路复盘器，例如异常复盘或系统恢复复盘。
- `ReviewTrigger` 是控制层对象，不是原始日志；它必须引用事实证据，但不能等同于调试输出。

## 统一处理闭环

1. `Preflight Validation`：步骤启动前先做前提与目标校验。
2. `Step Watchdog`：步骤执行中持续监视进度、路径推进和目标有效性。
3. `Runtime Health Monitor`：运行时全局监视连接、插件、底层接口与未捕获异常。
4. 一旦命中异常：
   - 立刻取消当前步骤的执行上下文。
   - 停止底层导航、交互或资源占用。
   - 记录最后有效进度与失败证据。
   - 生成 `ReviewTrigger` 并挂入当前计划会话。
5. `Review` 阶段只基于最新 `ReviewTrigger`、最近增量事实和派生状态做决策，不直接扫原始运行时对象。

## 检测职责分层

- 步骤前校验器：
  - 负责 `precondition_invalid` 与一部分可提前发现的 `target_invalid`。
  - 在动作真正起跑前，把“缺工具、背包满、目标已不存在、距离超界、交互前提不成立”提前挡下。
- 路径看门狗：
  - 专门负责 `path_invalid`。
  - 只关心“是否有真实推进”，不负责解释全局任务要不要改。
- 目标验证器：
  - 负责目标在执行中的持续有效性判断。
  - 当目标实体消失、目标方块变化、容器状态失效、主人不在可交互范围时触发 `target_invalid`。
- 系统健康监视器：
  - 负责 `system_exception`。
  - 监视断连、插件装载失败、关键接口异常、未捕获错误、底层会话不可用。

## 四类异常的判定边界

### path_invalid（路径失效）

- 定义：
  - 当前步骤依赖位移推进，但导航无法形成有效路径，或者持续执行后没有产生可接受的空间推进。
- 典型命中条件：
  - 路径求解失败。
  - 路径反复重算仍不可达。
  - 在设定窗口内位移增量低于阈值。
  - 被地形、门、实体碰撞或狭窄空间卡住。
- 最小证据：
  - 目标坐标或目标实体引用。
  - 步骤开始位置。
  - 最后有效推进位置。
  - 本次无进展持续时长。
  - 最近一次路径求解或重算失败原因。
- 本地动作：
  - 立即停止导航。
  - 清理移动控制状态。
  - 写入“最后有效位置”和“路径失效原因”。
- 复盘语义：
  - 默认视为步骤级可恢复异常。
  - 复盘层可选择重试路径、换接近点、换交互角度、换技能实现，或者放弃该步骤。
- 恢复边界：
  - 只有当步骤目标未失效且前提仍满足时，才允许在新路径下恢复旧步骤。

### target_invalid（目标失效）

- 定义：
  - 计划当前绑定的目标引用已不再可信，继续执行会造成空操作、错操作或误操作。
- 典型命中条件：
  - 目标实体消失、死亡、超出可追踪范围。
  - 目标方块已被破坏、替换或不再满足材质条件。
  - 目标容器状态变化，已无法打开、已被清空或已不属于原目标。
  - 主人、跟随对象或交互对象不再处于允许范围内。
- 最小证据：
  - 目标类型与目标标识。
  - 最近一次成功解析目标时的事实快照引用。
  - 当前验证失败原因。
  - 最后一次确认目标有效的时间。
- 本地动作：
  - 停止当前步骤。
  - 解除该步骤对旧目标的占用或引用。
  - 写入“目标失效”事实，而不是伪装成普通失败。
- 复盘语义：
  - 默认视为计划级异常。
  - 复盘层需要决定是重新获取同类目标、改用备选目标，还是整体换计划。
- 恢复边界：
  - 默认不直接恢复旧步骤；除非复盘层重新解析并明确确认新的目标绑定已经建立。

### precondition_invalid（执行前提失效）

- 定义：
  - 当前步骤的必要条件不成立，继续执行只会浪费时间或导致错误副作用。
- 典型命中条件：
  - 缺少工具、材料、权限或关键能力。
  - 背包已满，无法接收目标产物。
  - 当前姿态、距离、朝向或环境不满足交互条件。
  - 步骤执行中前提被破坏，例如工具损坏、资源被消耗完。
- 最小证据：
  - 缺失的前提项列表。
  - 当前已具备的相关能力或资源快照。
  - 最近一次前提检查通过的时间或步骤阶段。
  - 导致前提失效的直接原因。
- 本地动作：
  - 阻止步骤起跑或中止正在进行的步骤。
  - 写入“前提缺口”事实。
  - 将缺口暴露给复盘层，而不是让技能内部静默兜底。
- 复盘语义：
  - 默认视为计划级异常。
  - 复盘层需要决定先补前提，再回到原计划，还是重写计划。
- 恢复边界：
  - 只有当缺失前提被显式补齐，并重新通过步骤前校验时，才允许恢复相关计划片段。

### system_exception（系统级异常）

- 定义：
  - 底层会话、插件装配、关键接口或运行时本身出现故障，导致当前计划已不能建立在可信执行环境上。
- 典型命中条件：
  - 与服务器断连。
  - 关键插件缺失、卸载失败或状态损坏。
  - 底层接口调用抛出未恢复异常。
  - 运行时进入不可继续信任的错误状态。
- 最小证据：
  - 故障组件名称。
  - 错误类型或异常栈摘要。
  - 运行时健康状态摘要。
  - 当前会话是否仍然可用。
- 本地动作：
  - 立即冻结或终止当前步骤上下文。
  - 进入安全停机或等待恢复状态。
  - 阻止新的高风险执行继续入场。
- 复盘语义：
  - 这是运行时级异常，不与普通步骤失败同级。
  - 若系统尚未恢复，复盘层不能假装继续做正常任务规划，而应进入恢复规划。
- 恢复边界：
  - 默认不恢复旧计划。
  - 只有在会话重建、插件复位、关键接口重新可用后，才允许重新生成计划。

## Review 输入契约

- 复盘层读取的不是一句“失败了”，而是一份受控的 `ReviewInput`：
  - 当前 `ReviewTrigger`
  - 最近的步骤级增量事实
  - 当前派生状态
  - 最近一次成功验证的关键事实
  - 已执行的本地止损动作
  - 旧计划中尚未完成的步骤摘要
- 对四类异常，复盘层的目标分别是：
  - `path_invalid`：重新找到到达方式。
  - `target_invalid`：重新绑定目标或重写任务意图。
  - `precondition_invalid`：先补齐缺口，再决定是否恢复。
  - `system_exception`：先恢复系统执行条件，再考虑重新规划。

## ts-core 最小落地边界

- 为了避免继续停留在纯文档阶段，`ts-core` 的第一批最小落地对象固定为：
  - `ReviewTrigger`：统一承载四类异常进入复盘层时的控制对象。
  - `ReviewInput`：复盘层消费的最小输入。
  - `PathWatchdog`：第一批真正落地的检测器，只负责把“无进展”转成 `path_invalid`。
  - `PreflightValidator`：第二批最小检测器，只负责把“前提缺口”转成 `precondition_invalid`。
  - `BotActor.recordReviewTrigger`：运行时统一接收复盘触发的入口。
- 第一阶段不要求这些对象立刻接上真实 `mineflayer` 导航，但命名、字段与职责必须先固定，避免后续实现时再次改口。
- 当前最小落地顺序固定为：
  1. 先固定 `ReviewTrigger` 与 `ReviewInput` 类型。
  2. 再用 `PathWatchdog` 打通 `path_invalid` 的最小闭环。
  3. 再用 `PreflightValidator` 打通 `precondition_invalid` 的最小闭环。
  4. 后续按同样模式补 `target_invalid` 与 `system_exception` 的检测器。
