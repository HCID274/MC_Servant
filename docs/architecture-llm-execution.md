# LLM Execution Architecture

## 已确认原则

- 不采用传统的 `JSON` 作为主执行规划载体。
- 主方案固定为受限 `DSL`，而不是自由脚本执行。
- `LLM` 产出的是受限调用脚本，其能力边界由宿主预先暴露的接口决定。
- 命令行调用是当前优先方向，但执行环境边界仍需继续细化。

## 当前决定

- 选择“方案 A：受限 `DSL`”作为主路线。
- 不选择“让 `LLM` 自由生成任意 `JavaScript` 或 `TypeScript` 并直接运行”的主方案。
- `LLM` 的主输出不是单一步骤，而是一段受限计划：包含步骤列表、局部 `if else` 分支与失败后的回退意图。
- 上层主流程采用 `Plan-Execute-Review`，而不是“每次只生成一个原子动作”的单步模式。
- 后续设计重点应放在：接口暴露边界、错误返回方式、执行沙盒是否需要以及需要到什么强度。

## 当前未决问题

- 受限 `DSL` 的宿主形式是什么：命令式函数集合、链式调用还是更窄的执行句柄。
- `LLM` 生成的脚本由谁编译、谁执行、谁回收资源。
- 是否引入沙盒，以及沙盒对文件系统、网络、时间与内存的限制边界。
- 执行失败后返回给上层的是结构化错误、运行日志，还是两者同时保留。

## 后续文档职责

- 本文档只固定主路线与约束，不直接替代具体模块接口设计。
- 若后续对 `DSL` 形态、沙盒策略、返回格式达成共识，应继续更新本文档，而不是把细节写回 `AGENTS.md`。
